# データ更新処理の開発・変更時の検証

## 適用範囲

DB、スプレッドシート、ファイル、外部APIのデータを作成・更新・転記・削除する機能を追加・変更するときに適用する。表示だけの変更など、更新に関係しない作業では不要。対象と影響に応じて該当項目を選び、未確認事項を明記する。

## 実装前に確認すること

- データの作成から更新までの経路を確認する。手入力、コピー・貼り付け、並べ替え、インポート、別スクリプトやAPIによる更新のうち実際に使うものを対象にする。
- IDやキーの一意性の範囲、採番するタイミング、コピー時の扱い、更新対象の判定条件を確認する。ユーザー操作で崩れる条件を、コード内部だけの保証で済ませない。
- 入力トリガーが発火しない経路があるか確認する。該当経路の整合性をどこで保証するか決める。
- 関係する既存データを読み取りだけで検査し、重複、欠損、型や日付形式の違い、対象範囲から外れた列を確認する。本番アクセスが許可されない場合は匿名化データ等で検証し、本番未確認と報告する。
- 不整合なデータは検出と修正を分ける。別案件か不明なIDを推測で振り直したり、検証のために本番を修正したりしない。

## 停止・再実行の検証

- 処理の実行順と書き込み境界を確認する。各エラー時に、更新済みのデータ、未実行の処理、ロールバックの有無を説明できるようにする。
- 正常系に加え、関係する入力操作、重複・欠損、途中停止、再実行をテストする。同じ処理を再実行しても二重登録・消失・意図しない上書きが起きないか確認する。
- 転記後の元データ削除は、転記完了を保証できる順序またはトランザクションで行う。保証できない部分は制約として記載する。
- タイムアウト等で成功・失敗が不明な場合は、状態を読み戻して判断する。更新要求を無条件で再送しない。
- 不具合では、再現した発生経路を回帰テストに残す。検出しただけの原因候補と、実際の発生操作が確認された原因を区別する。

## 本番反映前後の確認

- 書き込みなしの更新計画または同等の検証で、更新・転記・削除の対象、件数、対象外データへの影響を確認する。
- バックアップ・復旧方法を対象に応じて決める。既存の承認ルールとユーザーからの実行許可を守る。この確認手順自体は本番操作の許可にならない。
- 実行後は読み戻しで対象件数、IDの一意性、転記内容、元行の扱い、対象外データの保持を確認する。

## ハーネスへの組み込み方

- 本ファイルを生成先の `.agents/skills/development-workflow/references/data-update-verification.md` に配置する。既に同等の共通手順がある場合はそちらへ統合し、重複を作らない。
- AGENTS.mdには適用条件と共通手順への参照だけを記載する。常時守る制約は既存Rulesへ、具体的なID仕様・更新順序・再実行仕様は関連Docsへ記載する。
- implement-feature、fix-bug、review-code、releaseから、データ更新に関係する場合だけ共通手順を参照させる。必ずしも専用Skillを追加する必要はない。
- Verificationでは、実施した操作・停止・再実行の検証と結果を報告する。未実施や適用外は理由を記載する。該当する重要条件が未確認の場合、無条件にリリース可能・恒久対策完了と判定しない。
- 新規プロジェクトでは設計段階で検証方法を決め、実装後に実証する。既存プロジェクトでは現在の動作・運用と照合してから変更する。

## 今回の教訓を適用する例

記録IDを列に追加する場合、採番処理だけでなく、行コピーによるID複製、ID列を含まない並べ替え、編集トリガーが発火しないAPI更新も検証する。別案件と判別できるコピーだけ再採番し、不明な重複は位置を示して更新前に停止する。

重複を検出して停止できることと、重複の発生を防げることは、それぞれ別の検証項目とする。
