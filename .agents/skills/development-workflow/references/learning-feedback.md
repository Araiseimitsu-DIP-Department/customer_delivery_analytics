# 不具合から得た学びの提案・承認・反映

## 適用タイミング

開発・改善・不具合対応で原因や確認漏れが分かったとき、ユーザーから追加依頼がなくても、再利用できる学びがあるか判断する。原因調査中は候補として扱い、確定した事実と推測を分ける。進行中の依頼を優先し、無関係な監査や定期監視を始めない。

## 提案するかの判断

- 他の機能やプロジェクトでも同じ確認漏れが起こり得るか。
- 既存のルール・手順・テストに不足があるか。既存ルールの実行漏れなら、まず参照・適用の経路を改善する。
- 実証された発生経路や検証結果を基に、適用条件を限定した具体策にできるか。
- 重複するルールや不要な承認を増やさずに統合できるか。単発の事情や未確認の原因を一般ルールにしない。

## 承認前に準備すること

1. templatesと対象プロジェクトの既存ルール・Skillsを読み、適切な反映先を決める。制約はRules、手順はSkills、仕様はDocs、発生経路の検証は回帰テスト、履歴はdocs/update.mdとする。
2. 学びの根拠、適用条件、変更するファイル、追加・修正する具体的な内容を整理する。既存内容への統合を優先する。
3. 必要な変更案は許可された作業領域内に準備して検証する。承認を得る前にtemplatesや対象プロジェクトの共通ルールへ反映しない。
4. ユーザーへ簡潔に提案し、その具体的な変更案への承認を得る。返答がないことを承認と扱わない。複数の関連変更はまとめて確認する。

## 承認後の反映

- 承認された対象・内容だけを更新する。元ファイルをバックアップし、準備後のユーザー変更を上書きしない。
- スキル形式、参照先、重複・矛盾、適用条件と承認条件を確認する。実行コードを変更する場合は必要なテストも実施する。
- 重要な変更はdocs/update.mdへ記録し、反映内容と検証結果を報告する。
- templatesの更新と既存プロジェクトへの適用を区別する。既存プロジェクトへの展開、コード変更、本番操作、pushは別途その範囲の承認が必要であり、テンプレート更新への承認だけで行わない。
- 見送られた場合は反映しない。同じ案を繰り返し提案せず、追加の根拠や新しい発生があるときに再評価する。

## ハーネスへの組み込み

本ファイルを生成先の `.agents/skills/development-workflow/references/learning-feedback.md` へ配置する。同等の手順がある場合は統合する。AGENTS.mdには適用タイミングと参照先を短く記載し、development-workflow・fix-bug・review-codeから必要時に参照させる。

この手順の採用は、今後の個別変更への包括的な承認ではない。AIが候補の判断と提案を行い、ユーザーが具体案を承認してから反映する。
